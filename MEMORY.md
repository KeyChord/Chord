- Macros live in `ChordSequence`; `ChordInputManager` hydrates named definitions from `named-macros.json` at startup and saves persistent updates before applying them. Named macros persist unless their name starts with an ASCII digit (0–9); numbered buffers are always temporary. All survive input resets/config reloads. Core setters are `0b<1–9><sequence>` and `0=<name>=<sequence>`. References `\1`–`\9` and `\name=` (leading `=` optional: `\=name=`) expand recursively before repetition, matching, and handler captures. Named references always require their closing `=`, even at the end of input. The leading `=` is needed for names starting with 1–9 (buffers) and, in text only, for names starting with `n`/`up`/`left`/`down`/`right`, because text gives special-key escapes precedence (`parse_text_macro_reference`; user-chosen 2026-10-16 so `/w]\n/wd=1` keeps meaning Enter). Internal expansion always goes through the canonical `ChordMacroName::reference()` (`\=name=`). The UI shows `\name=` unless one of those prefixes needs `=`. Settings → Macros uses the `chord-macros` observable and shared backend mutations to add/edit/rename/delete definitions and edit buffers. Renaming across the digit-prefix boundary updates persistence. Its sequence fields are multiline textareas: each line break is an Enter key press, stored as `\n` notation (`macro-sequence-text.ts` converts both ways); row previews mark every Enter with ↩, including a trailing one, and ⌘Enter saves. Setters save bodies verbatim, but a typed `\1`–`\9` or `\name=` has already been replaced by the macro's contents, so only text/CLI setters keep a live buffer reference. Missing/incomplete references stay pending; recursion, depth, expansion count, and output size are bounded. The 2026-10-15 environment inspection reconfirmed the Tauri/non-React-Native setup below.

In-flight JS callbacks finish on halt to preserve other handlers in their package worker. `\up`, `\left`, `\down`, and `\right` parse as physical arrow keys.

- Command grammar (`models/chord_command.rs`): `<count><`config`><chord>[⏎<chord>…]`. The backtick config block follows the count (or starts the input) and holds comma-separated options, digits in 100 ms: `d` = one digit, a single delay before the first run only (never per loop iteration; `` `d5`ab `` delays any chord), `i` = one digit per interval between runs, cycled, `0` = immediate (`` 3`d2,i130`/ws] ``). Each option at most once. A quote's block takes only `i`. Handlers keep the window focused at input completion, even after a delay. Enter is an ordinary key everywhere (buffer, `\n` text notation, triggers); the only hardcoded role is that the run parser splits chords at Enter after a count or config block. The user rejected a configurable separator. Loops, configured delays/intervals, and multi-chord runs become a `ChordPlan` (haltable background run in `chord_loops.rs`); plain `12ab` keeps in-task `num_times`. Earlier chords get isolated handler scopes and the typed chord keeps its typing scope; the plan releases all of them when it ends.

- Handler builders (default exports) run once per configuration load, never per execution; repeats and loop iterations call the built handler again. Each queued run with a completed input selects the focused window once (`select_run_window` in `chord_loops.rs`, AX on a blocking thread via `app/frontmost/focused_window.rs`) and stores it in every handler task and plan step as `HandlerChordAction.focused_window_id`, exposed as `this.focusedWindowId` (`null` while typing or when unavailable). Window-targeting handlers must use it instead of re-reading focus per iteration.

- Quotes / insert mode: typing `'` at a step start opens a quote; a buffer ending in an open quote is insert mode (`ChordCommand::Insert`, `ChordInputState.inserting`). The controller (`app/controller/app_mode.rs`) keeps Chord active without Space: Caps+Space → `finish_insert` (appends the closing `'`; `on_normal_mode_started` turns Caps Lock off), Esc → idle (discards everything), other keys → `type_into_quote` (Shift and modifiers from event-ordered `held_keys`, plus the OS Caps Lock toggle read per letter, Mac-style: Caps Lock + Shift stays uppercase; repeats of keys held before insert mode, like Space, are ignored). Quote text lives beside the keys: a typed quote is an adjacent `''` pair in `input`, its text in `quotes` (`ChordInputState`/`ChordInputEvent`), consumed in order by `parse_steps`. Text notation `'abc'` still works for CLI/TOML. `ChordTaskAction::Type { text, intervals_ms }` types via `Key::for_text_char` (US layout, Shift held for shifted chars) in `app/chord_runner/typing.rs`; `` `i#` `` after the quote sets cycled per-character intervals.

- Chord owns the Caps key (implemented 2026-10-16): the input owner remaps Caps 0x700000039 → F20 0x70000006F in system `UserKeyMapping` (`app/keyboard/caps_remap.rs`, state file `com.leonsilicon.chord/caps-remap-v1/state.json` with holder PID+start time and displaced entries), so macOS never toggles Caps Lock and Chord is its only writer. F20 reaches the tap in order (`tap.rs` decodes it as Caps; repeats swallowed; flagsChanged keycode 57 = mapping was removed → reinstall). `caps_lock_guard.rs`: plain tap turns off at key-down, on at release; normal mode keeps it off; chord end / ownership loss restores the pre-Chord state; insert-mode toggles aren't kept. Caps events are applied on the controller thread before routing. Secure Input fallback: Carbon hotkey F20 (`caps_hotkey.rs`, only fires when the tap can't see the key). Crash safety: launchd agent `<identifier>.caps-guardian` (`caps_guardian.rs`, hidden `chord __caps-guardian --state`, KeepAlive PathState on the state file, kqueue on holder exit) — verified end-to-end with a scratch agent. No raw HID listener, no polling, no timing margins. Lock-state reports from `IOHIDSetModifierLockState` (keycode 255 per keyboard, then the next key's code) are recognized in the tap by "only the AlphaShift flag changed vs. the previous device event" and rewritten in place to keycode 57 (first report) or swallowed (repeats), owner only — no app list. Input Monitoring is no longer required (Accessibility covers the active tap; IOHIDCheckAccess reports listen access granted for Accessibility-only apps). VoiceOver warning: `app/keyboard/voice_over.rs` + Activation Trigger settings card, shown when the VoiceOver4 domain exists and `SCRKeysToUseForVOModifier` != 0. Avoid spawning processes in lib tests: two such tests made the parallel lease tests fail in 4 of 12 runs (0 of 12 without), likely because a child mid-spawn holds their lock fds.

- Typed escapes (`models/chord_escape.rs`) never auto-expand: a Backslash key in the buffer keeps the input pending until Tab (`select_escape`) replaces the trailing escape with a special key it spells exactly, else the first match: named macros in name order matched with or without the leading `=` (full expansion inlined), then `\up`/`\left`/`\down`/`\right`/`\n`. Complete macro references are the exception: typing a buffer's digit (`\1`–`\9`) or a named macro's closing `=` (`\name=` or `\=name=`), as an unshifted or shifted press, immediately replaces the reference with its full expansion (`expand_typed_reference`, called by the input manager whenever a key is appended). Unexpandable references stay as typed; undefined ones make execution fail with "`<ref>` references an undefined macro" (`undefined_reference`), and leftover buffer references in text still expand at dispatch (`expand_typed_input`). Text (TOML, CLI via `ChordMacros::resolve_named`) still parses notation directly. The frontend suggestion list marks the same `active` entry.

- Shift blocks (user-designed 2026-10-29; replaced "shifted completion", which ran input on a shifted key and swapped the last key of the previous chord): keys typed with Shift held form blocks, a sticky prefix that survives runs. `ChordInputState.blocks` holds ascending input lengths where solid blocks end; `open_block` means Shift is held after a shifted key and every key after the last block (loose keys typed before Shift included, so `g ⇧d` is one `GD` block) is the block being typed. Any key event without Shift (`event.shift_key`) closes it; a typed `'` closes it first because insert mode never sees Shift's release. Runs (`set_executed_event`, `fail_input`, keyboard-only `clear_loose_keys`) reset the buffer to `block_input()` (blocks plus an open block, with their quote texts via `typed_quote_count`). Only keys after the blocks make input runnable (`has_loose_keys`): Caps with only blocks repeats `selected_input_event`, Space release with only blocks runs nothing. Backspace pops a loose key, else the whole last block; Esc and Shift+Backspace (`clear_key_buffer`) clear blocks too; exiting chord mode resets them. Every buffer edit goes through `rebase_blocks` (cuts block ends at the first changed key, so typed-reference expansion and Tab stay consistent). The panel tints block keys sky (dashed while open) and separates adjacent blocks.

- Failed executions (CapsLock, Space release) keep the input on screen: `ChordInputManager::fail_input` moves it to `selected_input_event` (the buffer keeps only its blocks) and sets `chord-input.error`, which the panel renders as red keys with the message in place of the chord name. `ChordSequenceDispatch.error` explains unresolved input (no chord found, chord named within sequences, pending/escape awaiting Tab); chords that only handle keyboard events are not errors. Resolve errors and later handler/loop failures also set it, guarded by an execution counter so only the still-shown chord is marked. Every state literal that clears `selected_input_event` must also clear `error`.
